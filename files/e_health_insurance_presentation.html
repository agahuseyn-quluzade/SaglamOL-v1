Monorepo Multi-Module Microservices
02

SaglamOL **Gradle Multi-Module Monorepo** strukturuna malikdir və hər bir servis öz məlumat bazası ilə izolyasiya olunmuş şəkildə fəaliyyət göstərir. Servislər arası əlaqə həm sinxron REST Feign client-lər, həm də asinxron Kafka event-ləri vasitəsilə baş tutur.

İnfrastruktur Eureka, Spring Config Server, API Gateway (Spring Cloud).
Məlumat Bazası Hər bir servis üçün ayrılmış PostgreSQL + Liquibase miqrasiyaları.
Asinxronluq Outbox pattern əsaslı Kafka mesajlaşması.

8 Biznes Servisi və Ortaq Paylaşılan Kitabxanalar
03

🔐 IAM & User Profile

İstifadəçilərin qeydiyyatı, BCrypt ilə şifrələmə, JWT Access Token və One-time Refresh Token fırlanması. Pasiyent, həkim, xəstəxana və sığorta agentlərinin fərdi profilləri.

🛡️ Policy & Claim

Sığorta limitləri, Redis ilə sürətli coverage rule kəş-i. Optimistik lock ilə eyni anda baş verən claim-lərin qarşısının alınması. İddiaların DRAFT-dan APPROVED-ə qədər status transition maşını.

🧠 AI Risk & Fraud

Xarici LLM/ML provayderi vasitəsilə 10s limitli iddia qiymətləndirməsi. Duplicate sənəd, limit sui-istifadəsi və şübhəli zaman intervalı kimi 4 əsas qayda ilə fırıldaqçılıq analizi.

Ortaq Paylaşılan Modullar (Common Libraries)

common-events: Event Envelope və bütün Kafka event payload tipləri. common-kafka: Outbox publisher və idempotent consumer dəstəyi. common-security: JWT validation filter, Rol sabitləri və Auth context.

Asinxron Event İnteqrasiyası

Transactional Outbox və Idempotent Consumer Pattern
04
// Biznes transaksiyası daxilində outbox-a yazmaq outboxEventService.saveEvent( "CLAIM", claimId, "ClaimSubmittedEvent", new ClaimSubmittedEvent(claimId, patientId, totalAmount) ); // @Scheduled scheduler hər 5s-dən bir işə düşür, // PENDING event-ləri Kafka-ya göndərir.

Niyə bu pattern?

Məlumat bazasında məlumatın dəyişdirilməsi ilə Kafka-ya event göndərilməsinin **eyni transaksiyada atomik** baş verməsini təmin edir. Şəbəkə xətası və ya Kafka çöküşü zamanı məlumat itkisi olmur.

  • Xəta baş verdikdə **Exponential Backoff** ilə yenidən cəhd (1dk, 5dk, 15dk).
  • Maksimum cəhd aşıldıqda event **DLT (Dead Letter Topic)**-ə göndərilir.
  • İstehlakçı tərəfdə processed_events vasitəsilə **Idempotency yoxlanışı** duplicate emalların qarşısını alır.

Biznes Qaydaları & Limit yoxlanışı

İddia təsdiq edildikdə limit rəsmən istifadə edilmiş sayılır. Rədd edildikdə rezervasiya azad olunur. Eyni anda gələn istəklər üçün `Optimistic Locking` (`@Version`) tətbiq olunur və 3 dəfə retry mexanizmi var.

AI Risk & Fırıldaqçılıq Analizi

Süni İntellekt Qiymətləndirməsi və Qayda-Əsaslı Fraud Təyini
06

🤖 Xarici AI / LLM İnteqrasiyası

İddia göndərildikdə AI Risk servisi xəstə tarixçəsi və iddia məlumatları əsasında risk səviyyəsini (LOW/MEDIUM/HIGH) və inam dərəcəsini hesablayır.

  • Xarici API zəngi üçün 10 saniyəlik timeout tətbiq olunur.
  • Şəbəkə və ya xarici servis xətalarında 3 dəfə (1dk, 5dk, 15dk) yenidən cəhd.
  • Bütün cəhdlər uğursuz olarsa, iddia avtomatik olaraq MANUAL_REVIEW_REQUIRED statusuna yönləndirilir (Həssas Fallback Modeli).

🛡️ Fraud Qaydalar Mühərriki

Fraud Detection servisi iddia məlumatlarını 4 əsas fırıldaqçılıq siqnalına əsasən analiz edir:

1. DUPLICATE_DOCUMENT: Eyni SHA-256 hash və ölçüyə malik sənədin digər klinika və ya xəstə tərəfindən yüklənməsi.
2. SUSPICIOUS_TIMING: Eyni xəstənin 7 gün ərzində eyni kateqoriyalı xidmət üzrə müraciət etməsi.
3. COVERAGE_ABUSE: İddia məbləğinin ortalama xidmət dəyərindən 2 dəfə çox olması.
4. FREQUENT_CLAIMS: Xəstənin son 30 gündə 5-dən çox iddia irəli sürməsi.

S3 Tibbi Sənəd Yükləmə İnteqrasiyası

MinIO/S3 ilə Atomik Upload Modeli
07

Səhiyyə sənədlərinin (müalicə fakturaları, həkim rəyləri) yüklənməsi zamanı bazadakı metadata ilə S3 (MinIO) anbarındakı faylın **bütövlüyünü (atomikliyini)** təmin etmək üçün iki fazalı model tətbiq olunur.

Faza 1: Metadata qeydi
Məlumat bazasında sənəd metadatası PENDING_UPLOAD statusu ilə qeyd olunur və tranzaksiya tamamlanır.
Faza 2: S3 Yükləmə və Təsdiq
Fayl S3 anbarına yüklənir. Uğurlu olarsa hash (SHA-256) hesablanır, status CONFIRMED edilir və Kafka-ya outbox event göndərilir. Xəta olarsa status UPLOAD_FAILED olur.

Orphan (Yetim) Faylların Təmizlənməsi

Əgər istifadəçi fayl yükləməni başladarsa, lakin şəbəkə kəsildiyi üçün S3 yüklənməsi baş tutmazsa bazada status PENDING_UPLOAD olaraq qalır.

⚠️ Cron Job: Hər saatda bir çalışan arxa plan tapşırığı 1 saatdan köhnə olan PENDING_UPLOAD sənədlərini aşkar edərək statusu ORPHAN_CANDIDATE-ə dəyişir və təmizləyir.

Niyə SaglamOL?

SaglamOL platforması e-səhiyyə sığortası sahəsində ən kritik məsələlər olan **təhlükəsizlik**, **məlumat bütövlüyü (Outbox)**, **genişlənəbilən arxitektura** və **Süni İntellekt dəstəyi ilə avtomatlaşdırmanı** bir araya gətirir. Bu sistem biznesə sığorta iddialarının sürətli emalını təmin etməklə fırıldaqçılıq riskini minimuma endirməyə imkan verir.
